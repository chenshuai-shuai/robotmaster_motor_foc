# 规范 · 编码规范（工程 v1.0）

> **用户 2026-09-19 提出的目标**：代码要够先进、可维护、可持续演进；**每一行都要是高质量代码**；并希望借鉴编程先驱们的成熟思想。
>
> **本文的立场**：高质量不是形容词，是**可执行、可检查、可复现**的东西。
> 凡是不能机械检查的规则，就必须进"提交前审查清单"；凡是不能落到清单或脚本里的，就只是口号——**口号不写进规范**。

## 1. 我们借用谁的思想（以及在本工程怎么落地）

| 来源 | 主张 | 在本工程的落地条款 |
|---|---|---|
| **Dijkstra**（1970《Notes on Structured Programming》） | "程序测试只能证明存在 bug，永远不能证明没有 bug" | 不靠"跑过就算对"：**静态断言 + 编译期依赖检查 + 宿主机穷举单测**当作第一道防线（§3） |
| **Hoare**（1980 图灵奖演讲） | 设计要"简单到显然没有缺陷"，而不是"复杂到看不出缺陷" | 契约头（每模块只暴露 3 个函数）+ 单向依赖；**禁止过度抽象**（C-33） |
| **Dijkstra**（EWD498） | "简单是可靠的前提" | 模块边界用宏显式化；一个 `FEATURE_*` 只回答一件事（R1） |
| **Knuth**（1974） | "过早优化是万恶之源" | **先测量后优化**：时间预算表 + 实测 `dtmax`/`flush_ms`，编译器 `-O0→-O2` 放最后（§6） |
| **Lamport** | "写作是自然让你发现思维有多潦草的方式"；先写规格 | **方案先行**：设计→编码方案→才动代码（本工程已在执行） |
| **Holzmann / NASA-JPL《Power of Ten》**（2006） | 十条安全关键编码规则：限制控制流、循环必须有界、初始化后禁动态内存、函数短、断言密度、静态分析 | C-19..C-26（控制流）、C-13（禁实时路径 malloc）、C-27（函数 ≤60 行）、C-48（断言/自检密度） |
| **MISRA C:2012** | 用规则约束 C 的可移植性陷阱（整数提升、隐式转换、位运算类型） | C-01..C-06（类型与整数） |
| **Barr Group《Embedded C Coding Standard》** | 用命名与格式承载信息（模块前缀、单位后缀、禁止魔法数） | C-34..C-38（命名/常量） |
| **Rob Pike**（Go proverbs, 2015） | "Clear is better than clever"；"A little copying is better than a little dependency" | 禁止炫技宏/指针体操（C-33）；**不引入第三方框架**（UI 用 200 行自己的渲染器，不搬 LVGL） |
| **Fred Brooks**（《人月神话》1975） | 概念完整性（conceptual integrity）比功能数量重要 | 一套分层 + 一套命名 + 一套门禁，全工程一致（§7） |
| **Torvalds**（LKML 2000） | "Talk is cheap. Show me the code." | 每条"质量承诺"都要有对应门禁/证据（§3、§4 全部带行号证据） |

## 2. 硬性规则（可查、编号、违反即返工）

### 一、类型与整数

| # | 规则 | 为什么 |
|---|---|---|
| C-01 | 只用 `<stdint.h>` 定宽类型（`uint8_t`/`int32_t`…）；**禁止裸 `int`/`long` 出现在接口、结构体、时序计算里** | 跨平台/跨编译器行为一致 |
| C-02 | 位运算、移位、掩码**一律无符号**；先显式转换再运算 | MISRA 10.1/12.1：有符号移位是实现定义行为 |
| C-03 | 注意整数提升：`uint8_t a; ~a` 提升为 `int` → 必须写 `~(uint32_t)a` | 经典静默 bug |
| C-04 | 比较/循环计数**不许混有符号与无符号**（`-Wsign-compare` 必须为 0） | -Wall 会抓，别关警告 |
| C-05 | 浮点只用于**物理量**；ISR 与每周期高频路径避免浮点（本工程 F427 有 FPU，但上下文保存有开销） | 确定性优先 |
| C-06 | 单位写进变量名（`_deg`/`_dps`/`_nm`/`_ms`/`_us`） | 本工程已有传统（`sn.pos_deg`、`pos.vel_dps`），必须保持 |

### 二、并发与中断（本工程事故高发区）

| # | 规则 | 为什么 |
|---|---|---|
| C-07 | ISR 只做三件事：**搬字节、置标志、通知**；禁 `snprintf`/`LOG_*`/`HAL_Delay`/阻塞 API | 已有铁律（`CmdRx_RxIsr` 的注释就是教训） |
| C-08 | 中断与任务共享的变量 **必须 `volatile`**；RMW（读-改-写）必须临界区 | `volatile` 不保证原子性 |
| C-09 | 临界区 <10µs；ISR 里用 `FROM_ISR` 版本 API | 优先级反转/丢中断 |
| C-10 | **高优先级任务禁止长自旋**；所有"等硬件"的循环**必须带超时计数** | 实机教训：邮箱自旋 100000 → 饿死串口（`motor_8108.c` 改为 `++guard > 500u`） |
| C-11 | 跨任务数据只走三种通道：快照（seqlock）/队列/事件组；**禁止裸共享变量轮询** | 撕裂读（见 §4 反面教材） |
| C-12 | 屏/日志/遥测等"读者"只读快照，**绝不反向改控制状态** | 数据流单向（`ui_status.h` 的设计意图） |

### 三、内存与缓冲

| # | 规则 | 为什么 |
|---|---|---|
| C-13 | **实时路径禁止 malloc/free**；所有缓冲静态分配（显存/日志环形/缓存） | JPL Power of Ten 规则 3；本工程 heap 只给 RTOS 对象 |
| C-14 | 任务内栈上缓冲 ≤256B；更大的改 `static` | 任务栈是 640 words 量级，`char b[1024]` 是灾难 |
| C-15 | 缓冲区大小参数**成对出现**（指针+长度同进同出），访问前边界检查 | 越界是嵌入式第一杀手 |
| C-16 | 指针入参**必须判 NULL**（公开接口）；内部静态函数可省略但要注释"调用方已保证" | MISRA Dir 4.14 精神 |
| C-17 | 结构体**尺寸断言**：对协议帧/快照等有外部约束的结构，编译期或门禁里断言字节数 | 协议帧 8 字节不能变成 12 |
| C-18 | 显存/缓存等大数组集中在一个文件、`static`、注释写清字节数 | 便于 RAM 预算核对（MAP 证据） |

### 四、控制流与错误处理

| # | 规则 | 为什么 |
|---|---|---|
| C-19 | `switch` 必有 `default`；`if/else if` 链以 `else` 收尾 | MISRA 16.4 / 15.7 |
| C-20 | 所有等待循环必须有界 + 超时保护（含"等 SPI 完成""等邮箱空"） | JPL 规则 2；P1-5 就踩过无界自旋 |
| C-21 | **HAL 返回值必须检查**：`if (HAL_xxx(...) != HAL_OK) { 记录 + 兜底 }` | 静默失败 = 最难查的 bug |
| C-22 | 错误处理策略分三层且写进注释：**可恢复**（重试/降级）、**可上报**（`@ERR`/日志/告警位）、**致命**（进安全态，绝不 while(1) 死等） | 本工程 `Error_Handler()` 的 `while(1)` 只许出现在启动期 |
| C-23 | 状态机不许"魔法数"：状态/错误码全部枚举化 | 已有传统（`Ctrl_Mode_e`/`J8108_St_*`） |
| C-24 | 每个 `case` 必须能独立读懂（不许跨 case 隐式依赖） | 可维护性 |
| C-25 | 失败路径与成功路径**同等对待**（每个 `return` 都要想清楚调用方会怎样） | Dijkstra：正确性 = 所有路径都成立 |
| C-26 | **不许用返回值表达"内部状态"**——查询用独立只读接口 | 语义清晰 |

### 五、函数与接口

| # | 规则 | 为什么 |
|---|---|---|
| C-27 | 函数 ≤60 行、单职责；超了就拆（拆的是"职责"，不是"行数"） | JPL 规则 4 |
| C-28 | 一个模块 = 一对文件：**契约头**（Init/Status/SelfTest，任何宏组合可 include）+ 实现（全文被 `#if FEATURE_*` 包住） | 本工程模块化规范 R4/R3 |
| C-29 | **单向依赖**：UI→契约→驱动→寄存器。发现反向依赖（如控制任务 include UI 策略头）立即改 | 已有实例：`J8108_Task.c:23` 待修 |
| C-30 | 公开接口函数名带模块前缀（`Disp_`/`J8108_`/`Key_`）；纯内部函数 `static` | 可 grep、可静态检查 |
| C-31 | 函数头注释必须写四件事（缺一不可）：**输入范围 / 输出与副作用 / 时间预算 / 失败时的行为** | 本规范新增（比"@param"更有用） |
| C-32 | 不写"将来可能用到"的参数/分支（YAGNI）；加了必须有调用者 | 无用代码 = 负债 |
| C-33 | **禁止炫技**：宏里套宏、函数指针表（除非状态机需要）、位域打包协议（除非协议规定）、指针体操 | Pike：Clear is better than clever |

### 六、命名、注释与常量

| # | 规则 | 为什么 |
|---|---|---|
| C-34 | 命名风格统一：类型 `Xxx_Yyy_t`、枚举值 `XXX_YYY`、宏 `UPPER`、静态变量 `s_`、全局 `g_` | 现状已如此，保持 |
| C-35 | **硬件参数集中**：引脚/极性/波特率/尺寸/阈值一律宏，放 `board_config.h`（板级）或模块头（功能级）；**文件里不许有裸引脚值** | 用户既有铁律；硬件接反只改一处 |
| C-36 | 魔法数禁止：除 `0/1/-1/2/10/1000` 等语义显然者，一律命名常量（含"为什么是这个值"的来源注释） | 例：`OLED_I2C_HALF_PERIOD_US 2U` 带说明 |
| C-37 | 注释解释 **why**（原理/坑/取舍），不是 what（翻译代码）；中文写原理、英文写日志 | 用户铁律 5 + 日志 ASCII 约定 |
| C-38 | 每个文件头必须有：**职责 / 依赖 / 被谁调用 / 时间预算 / 已知坑** | 本规范新增（本工程已有雏形，统一成模板） |

### 七、时间、性能与确定性

| # | 规则 | 为什么 |
|---|---|---|
| C-39 | 每个任务/每个耗时调用都要有**时间预算**（写进文件头），并留 **≥2 倍余量** | 性能问题在嵌入式是"确定性"问题，不是平均值问题 |
| C-40 | 优化顺序固定：**算法 → 数据布局 → 编译器选项**；每一步都要有"改前/改后实测"证据 | Knuth；本工程当前 `Optim=1(-O0)`，是否升 `-O2` 由实测决定（§6） |
| C-41 | 禁止"看不见的耗时"：`HAL_Delay`（本工程 FreeRTOS 下禁用）、忙等、`printf` 大缓冲 | 已有教训（OLED 初始化期 HAL_Delay 卡死） |
| C-42 | 栈余量用实测高水位（`uxTaskGetStackHighWaterMark`）验证 ≥ **3 倍** | `stack_probe.h` 已在做，规范化阈值 |
| C-43 | RAM/Flash 占用必须在门禁里可见（MAP Grand Totals），超阈值（RAM>70%）即停手先算账 | 40KB 显存这种大件必须先算账 |

### 八、冗余与防御的边界

| # | 规则 | 为什么 |
|---|---|---|
| C-44 | **冗余 = 冗余的判据 + 余量**，不是重复的代码：安全关键路径要双判据（例：心跳超时 **且** 反馈不新鲜才退 DAMP） | 用户要"高冗余"的正确含义 |
| C-45 | 安全关键动作必须可确认（`#ZERO CONFIRM`）、必须可观测（`@EVT`/事件位）、必须有兜底态（DAMP 不失能） | 本工程已有模式，保持 |
| C-46 | **分层防御**：控制/安全层做穷尽判据；UI/显示层不做过度防御（不做无意义的重复判空、不做"以防万一"的重试） | 过度防御浪费 CPU/Flash 并掩盖真 bug |
| C-47 | 每个"断言/自检"必须说明**触发后系统做什么**（降级？上报？停机？） | 否则等于噪音 |

### 九、测试与证据

| # | 规则 | 为什么 |
|---|---|---|
| C-48 | 纯逻辑（可脱离硬件）**必须**写成可宿主机测试的模块，并进 `make verify` | 已有五类测试（key/motor/cmd/ctrl/uiact）；新增 disp_geom 照做 |
| C-49 | 每个模块提供 `Xxx_SelfTest()`（非破坏性），可经串口 `#ST` 调用 | 上机后的分块验证 |
| C-50 | 交付必须附**可复现证据**：`make verify` 全绿日志 + 台架回包 + MAP 尺寸 + 版本号/hex sha256 | Torvalds：show me the code；用户铁律：交付前核验 |

## 3. 机械化执行（把规则变成工具，而不是靠记性）

## 5. 每行代码的"四问" + 提交前审查清单

**写每一行/每个函数前问自己**（这是"高质量"的最小可执行单位）：
1. **副作用**：这行除了返回值还改变了什么？（`volatile`？硬件？其它任务可见的状态？）
2. **失败**：如果它失败/超时/返回错误，系统会怎样？谁负责兜底？
3. **并发**：谁会在中断/别的任务里同时碰它？我加锁了吗？还是它本来就只被一个人碰？
4. **预算**：最坏情况它要花多少时间/多少栈？我的余量够吗？

**提交前审查清单**（对齐现有 `embedded-c-coding` 技能 + 本规范）：

- [ ] GPIO/外设与原理图一致（原理图 → `.ioc` → 代码 三方核对）
- [ ] 硬件参数集中（无裸引脚值、无魔法数）
- [ ] `volatile`/临界区覆盖所有跨上下文共享变量
- [ ] 所有等待循环有界 + 超时
- [ ] 缓冲区成对传参、边界检查、指针判 NULL
- [ ] 无 `HAL_Delay`（FreeRTOS 下）、无长自旋、无 ISR 里 `printf`
- [ ] `switch` 有 `default`、`if` 链有 `else`、HAL 返回值已检查
- [ ] 栈估算（含 printf 链）与时间预算已写进文件头
- [ ] 未动 CubeMX 生成区；新外设初始化在 USER CODE 区
- [ ] 文件头五要素（职责/依赖/调用者/预算/坑）齐全
- [ ] 纯逻辑部分有宿主机单测；模块有 `Xxx_SelfTest()`
- [ ] **编译 0 Error 0 Warning**（Keil AC6）+ `make verify` 全绿
- [ ] 烧录实测通过（编译通过 ≠ 运行正确），并留下证据（日志/回包/hex sha256）
- [ ] 版本号已 bump（`tools/bump_version.py`）

## 6. "性能强劲"的正确做法（别跑偏）

1. **先测量，后优化**（Knuth）：本工程的性能指标是**确定性与余量**——
   - 控制环：`dtmax` ≤ 2ms（现状 1~10ms 波动，摘要可见）
   - 屏刷：单行带 ≤5ms、全屏 ≤35ms（彩屏 S2 实测）
   - 任务栈：高水位 ≤1/3
2. **优化顺序**：算法 → 数据布局 → 编译器选项。
3. **编译器优化（`-O0 → -O2`）放最后**，且必须附证据：
   - 判据：彩屏 S2 实测 `flush` 若 >8ms（单带）或控制 `dtmax` 劣化，则评估升 `-O2`；
   - 升 `-O2` 后必须重跑全部循环测试 + 台架（优化会暴露 `volatile`/别名问题）；
   - **不允许**为了"看起来快"改成难以维护的写法（Pike：clear > clever）。
4. **不引入第三方框架**：UI 自己写（约 200 行），不搬 LVGL/JS 风格 GUI——每一个依赖都是长期负债（Pike："A little copying is better than a little dependency"）。
