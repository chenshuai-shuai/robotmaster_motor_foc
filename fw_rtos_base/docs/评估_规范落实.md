# 规范落实评估（fw_rtos_base，2026-09-19）

> 目的：回答一个问题 —— **《规范_功能宏与模块化》《规范_编码规范》这套东西，是"写在文档里"，还是真的落地了？**
> 评估方式：不看承诺，只看**三样硬证据** —— ①代码里有没有 ②断言能不能自动查 ③实机跑出来对不对。

---

## 0. 一句话结论

**核心规范（R1–R7 + 门禁 V9–V13）已完整落地，且每条都有机械断言守着。**
剩下的不是"规范没落实"，而是**规范派生出的清理与收尾工作**（M7 死文件、SD 去留）与**尚未动工的下一阶段**（彩屏 S0–S5）。

| 维度 | 结论 |
|---|---|
| 规范条文落实率 | **R1–R7 全部落地**（其中 R5 部分：引脚常量走 `board_config.h` 而非 `CFG_*` 宏，见 §4） |
| 门禁落实率 | **V9–V13 全部落地**，一条命令可跑（`make verify` / `make profiles`） |
| 机械化程度 | 88 个 `check()` 调用 → 运行时展开 **97 项断言**，覆盖"宏/接线/协议/安全/诊断/手册一致性/裁剪/头自足" |
| 实机验证 | 5 个版本连续烧写（v0.1.60 → v0.1.66）全部 clean，且**改动前后的行为可逐字对照** |
| 附带收益 | 裁剪使 Code −2.5KB；同时新增自检+横幅 +1.3KB → 相对基线净 −1.2KB，**能力更多、体积更小** |

## 1. 评估判据（怎么算"落实"）

| 级别 | 含义 | 判定方式 |
|---|---|---|
| **L1 代码落地** | 规范要求的结构/接口真的存在于源码 | 读文件 |
| **L2 机械可查** | 有人反对也没用：断言能自动 FAIL | `make verify` / `make profiles` |
| **L3 实机证据** | 板子上跑出来与规范描述一致 | 串口日志 |
| 只有 L1 | **等于没落实**（文档里的表格）—— 这正是本次改造要消灭的状态 | |

## 4. 未落实 / 部分落实（诚实清单）

1. **R5 只落实了一半**：`CFG_*` 这类"板级/硬件宏"目前只有 `CFG_PROFILE` 一个；引脚/外设常量按 K5 决策集中到了 `board_config.h`（文件里的 `BRD_*` 常量），**不是 `CFG_*` 宏**。两种做法都能达到"换板只改一处"的目的，但**与 R5 的字面表述不一致**。→ 建议：要么承认 K5 是 R5 的等价实现（更新规范措辞），要么后续把 `BRD_*` 再包一层 `CFG_*`。**这个决定留给你。**
2. **Q1 / Q2 未入门禁**：`gcc -fanalyzer` 验证过能用但没进 `make`；函数长度门禁只写在规范里 —— 按"只有 L1 = 等于没落实"的判据，这两条**目前不算落实**。
3. **M7 清理未做**：`button.c` / `tlsf.c` / `dc_motor.c` 等不在编译集的历史文件仍在目录里；SD 集群去留未决。
4. **彩屏 S0–S5 未动工**：`FEATURE_DISP_ST7735S_SPI` 现在被一条临时 `#error` 拦住（防止选了驱动却链接失败），S1 落地时删除。
5. **R7 的"未编译模块"路径只在编译期验过**：`#ST disp` → `@ERR 9 … code=255` 走的 `MOTOR_DEV` 组合只有真编证据（4/4 PASS），**没有实机烧写验证**（可选）。

## 7. 结论

- **规范已落地**：R1–R7 主要条文、V9–V13 全部门禁都有代码 + 断言 + 实机三重证据；"文档里的表格"已经变成"跑一条命令就 FAIL 的检查"。
- **规范也确实"抓住过东西"**（这是它有用的最好证明）：
  - M1 抓到 2 个被单一配置掩盖的隐藏依赖（协议口/命令口）；
  - M3 的 fail-fast 抓到 10 个漏网依赖（`it.c`/HAL/FatFs 仍指着被清空的 SD 文件）；
  - M4 的 V11 抓到契约头不自足（`Led_Task.h` 缺 `<stdint.h>`）；
  - 台架抓到"汇总回包漏命令名"，并促成了"回包必须带命令名"的新断言。
- **待你决策 / 待办**：§4 的 5 项（R5 措辞、Q1/Q2 是否入门禁、M7 清理、彩屏 S1、可选的 MOTOR_DEV 实机验证）。
