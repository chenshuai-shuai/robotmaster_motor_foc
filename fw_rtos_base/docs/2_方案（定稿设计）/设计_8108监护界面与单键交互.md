## 1. v1 的缺陷在哪（你的质疑成立，这是根因）

v1 把 **使能⇄失能切换** 绑在"单击"上，而"单击"必须经过连击判定窗口：

```
想双击翻页的用户 → 第1次按下被判成 CLICK → 使能切了
再双击的手速稍慢（间隔 320ms）→ 判成两次独立 CLICK → 使能切两次（途中电机瞬间掉力又上力）
```

**根因：把"有状态后果的动作"绑在"会被连击窗口判定的手势"上。** 只要这两者还在一起，怎么调窗口参数都只是把概率调小，调不到零。
**结论（v2 原则）：连击类手势只做无副作用 UI 操作；一切电机动作必须"持续按压 + 松手生效 + 视觉进度反馈"。**

## 2. 按键安全设计（v2 重点）

### 2.1 动作分级：谁用什么手势（治本）

| 类别 | 手势 | 动作 | 误判的最坏后果 |
|---|---|---|---|
| **UI 类（零副作用）** | 单击 / 双击 | 光标下移 / 上移 | 光标多跳一格 —— 无害 |
| **电机类（有状态后果）** | **长按 2s（松手生效）** | 由**光标选中行**决定（v1 = 使能 ⇄ 失能） | 需按住 2s 且进度条走满并主动松手；中途松手 = 取消 |

→ **使能/失能再也不会因为"单击被判成双击"而误触发**：它根本不吃单击。

### 2.2 连击判定参数（回答你的问题：双击间隔多少算有效）

| 参数 | 值（可调宏） | 说明 |
|---|---|---|
| 采样周期 | 10 ms | 轮询，不用 EXTI（无中断上下文风险） |
| 消抖 | 30 ms | 连续 3 次采样一致才认可 |
| 短按有效时长 | **40 ~ 400 ms** | <40ms 视为抖动丢弃；>400ms 按长按处理 |
| **双击间隔窗口** | **80 ~ 300 ms**（第 1 次松手 → 第 2 次按下） | **<80ms** 判抖动丢弃；**80~300ms** 判双击；**>300ms** 判两次独立单击 |
| 三击（本版不用） | 窗口 1000ms 内累计 | 预留 |
| 单击动作延迟 | ≤300 ms | 等连击窗口才分派（因只影响 UI，延迟无害） |

> ⚠️ 关键：这套参数调歪的后果只有"光标多跳/跳错方向"，**与电机状态无关**——这才是真正的保护，而不是靠把窗口调到某个"刚好"的值。

### 2.3 四层防误触 / 防抖保护（电机类动作专属）

| 层 | 机制 | 作用 |
|---|---|---|
| **L1 手势把守** | 长按 **2s** 且**松手才生效**；按住期间屏幕显示进度条 + "将执行：使能/失能"；提前松手 = 取消 | 误触概率≈0；意图可见 |
| **L2 冷却锁定** | 任一电机类动作执行后 **1.5s 冷却**，期间所有电机动作请求一律忽略（屏幕提示 `HOLD`） | 杜绝"使能-失能-使能"抖动脉冲 |
| **L3 执行前校验** | 执行前检查 CAN 健康（最近 200ms 内有反馈帧）；失联 → **拒绝执行** + 屏幕提示 + 日志 | 不做"盲发" |
| **L4 执行后确认** | 发使能帧后 300ms 内应恢复反馈帧（**厂商文档：只有使能后才回传反馈帧**）；收到 → `EN ✓`；没收到 → `EN ?` + 告警日志 | 用**硬证据**确认，不做"我以为" |
| **L5 卡死检测** | 电平持续低 >10s（按键被压住/短路）→ 忽略该键 + 屏幕 `KEY STUCK` | 防物理卡死造成无限触发 |
| ~~L6 失能前 500ms 阻尼过渡~~ **（评估后取消）** | — | 挡不住失能后的重力下落，只是把"突变"变"渐变"，收益有限还易被误读成"安全了" → 用"阻尼模式"替代（见 §3.2） |

### 2.4 按键状态机（v2）

```
IDLE ──按下(消抖)──▶ PRESSED ──┬─ 松手且时长 40~400ms ─▶ clicks++ → WAIT_MULTI(300ms)
                              │        ├─ 窗口内再按 → clicks++（双击/三击判定）
                              │        └─ 窗口超时 → 分派 UI 事件（CLICK/DOUBLE）
                              └─ 持续按住 ─▶ [进度条] ─ 时长≥该行阈值(默认2s) 后松手 ─▶ 执行选中行动作（进冷却）
                                                   └─ 按住期间 CAN 失联 → 取消本次动作
```

## 3. 单页 UI 设计（v2：一页装全部，6×8 字体 8 行 × 21 字符）

取消多页面、取消菜单逻辑；**信息全在一页**，用"上下选中光标"定位。

```
>CAN OK 302Hz   EN ✓      ← 行1  CAN状态+帧率+使能（唯一有动作的行）
 POS  12.34r    88.4°      ← 行2  位置：电机端 rad / 输出端 度
 VEL   0.60r/s    5.7R     ← 行3  速度：rad/s / RPM(输出端)
 T     0.12Nm              ← 行4  前馈扭矩
 MOS    30C   COIL  27C    ← 行5  两路温度（超100℃ 整行反色）
 RX 258314   TX   960      ← 行6  反馈帧计数 / 发送帧计数
 dT    12ms   ES  0x0000   ← 行7  距上一帧(ms，>200=失联) / CAN 错误状态
 v0.1.42   UP  123s        ← 行8  版本 + 运行秒数（按键后临时变提示行 2s）
```

### 3.1 光标与长按的执行规则（2026-09-15 已确认）

- `>` 指示 + **选中行整行反色**（`OLED_ReverseArea`，很醒目）
- **单击 = 光标下移**（到底回绕）；**双击 = 光标上移**（纯 UI，零副作用）
- **长按（松手时判定）= 执行"光标选中行"的动作**：
  - 选中行**绑定了动作** → 执行：发通信包 + L3 前校验 + L4 后确认 + L2 冷却
  - 选中行是**只读行** → **什么都不发生**（不动作、不提示）
- **每行有自己的"最短按住时长"**（行属性）：v1 使能行 = **2s**；将来"零点"行 4s、"重启"行 6s —— 越危险的行自带越长把守，进度条按该行的阈值走满
- 这已经是菜单的雏形：**将来加动作 = 动作表加一行（含时长/条件），界面与手势零重构**
- 行1 光标选中且绑定了动作时，行尾显示长按将执行的动作（`[EN]` / `[DIS]`）

### 3.2 失能 ≠ 软住：L6 的结论（2026-09-15）

- **失能（FF..FD）= 驱动器关输出**：电机不再出力，带重力负载的关节会立刻自由下落——这是物理必然，**"失能前加阻尼"挡不住失能后的下落**，最多把"突变"变"渐变"，收益有限、还可能让人误以为已经安全。
- 故 v1 **不做 L6**。真正的保护是：①失能动作有屏幕警告 + 2s 进度条留出反应时间；②机械上先把负载支撑住（垫块/夹具/降到低位）。
- 若确实需要"松一点但不掉"：正确做法是**阻尼模式**（不发送失能帧，持续发 v=0 / Kp=0 / Kd=小值 的 MIT 帧 → 电机仍通电、提供粘滞阻尼，负载缓慢下滑而非自由落体），列为 M4 可选（单独一个光标行）。

**提示行（好记性不如烂键盘）**：任何按键动作后，行8 临时显示 `CLK=▼ DBL=▲ HOLD=EXEC` 2 秒

**刷新**：6×8 字体整屏 = 128×64 bit → 软 I2C 字节数比 8×16 少一半；先按 200ms 整屏刷新，实测耗时后若 >20ms 再改分区刷新（M1 实测）。

## 4. 状态可信度设计（新研究结论，直接决定屏幕怎么写）

研究来源：厂商单编文档 + 双编逆向笔记 + 我们已收到的真实帧。

| 想显示 | 能不能确认 | 依据 / 显示策略 |
|---|---|---|
| CAN 链路通不通 | ✅ 完全可确认 | 我们自己的计数器：反馈帧速率、ΔT、错误状态 → `OK / LOST` |
| 使能状态 | ✅ **有硬证据**：厂商文档明确"**电机需要使能后才会回传反馈帧**" → **有反馈帧 = 使能生效**；无反馈 + 我们发过失能 = 已失能；无反馈且状态不明 = `?` | 显示三态 `EN ✓` / `DIS` / `?`，绝不显示"确定失能"这种过度承诺 |
| 温度 | ✅ | byte6 = MOS ℃、byte7 = 线圈 ℃（解算已实测：0x4B→29.41℃、0x44→26.67℃） |
| 故障/保护标志 | ⚠️ **单编版暂无法确认** | 双编逆向固件里反馈帧第 8 字节 = **状态位（6 个保护标志 bit0..6）**；但**我们的单编厂商文档写 byte0 = 待定、byte7 = TMotor**，且实测 byte0 ≡ 0x01（= CANID，高 4 位疑似错误码位）。→ v2 处理：诊断行原样显示 byte0 原始值（留数据），将来若触发过温/堵转保护即可反推标志位；**不猜、不编** |
| 母线电压/输入电流 | ❌ 反馈帧里没有 | 若要显示需硬件引线（电机 24V 分压进 A 板 ADC）→ 列为可选，等你决定 |

## 5. 系统架构（不变部分，保留说明）

```
                 ┌──────────────────────────────┐
   PB2 ─────────▶│ Key_Task  (10ms, prio 4)     │
                 │ 扫描+消抖+事件机+长按进度     │
                 └───┬──────────────────┬───────┘
        UI事件(单击/双击) │                  │ 长按确认(松手)
                        ▼                  ▼
        ┌────────────────────────┐  ┌──────────────────────────────┐
        │ Oled_Task (5Hz, prio3) │  │ J8108_Task (1ms环, prio 5)   │
        │ 单页8行渲染+光标+告警  │◀─┤ 200Hz MIT 帧 / 1kHz 解算     │
        │ 读数据快照（双缓冲）   │  │ 动作表：使能/失能/…+冷却+L3/L4│
        └────────────────────────┘  └──────────────────────────────┘
```
- **显示必须独立低优先级任务**：软 I2C 刷屏毫秒级，放控制任务里会顶掉 200Hz MIT 帧（电机断流保护会踢）
- **事件标志组**（不是队列）：UI 事件与长按确认由不同任务消费，各等各自的位，互不干扰
- **双缓冲数据快照**：控制任务写、显示任务读，读侧永远拿到完整一帧，不阻塞控制

### 9.1 实现期发现并修掉的坑（M1）

## 11. M2 / M3 实现与"接电机"实机测试剧本（v0.1.46-dev）

### 11.1 关键硬件坑（本次新发现，务必记住）

本板 `Core/Src/can.c` 的 CAN1 配置为 **`AutoRetransmission = ENABLE`**（帧在无应答时会**无限重传**）+ `AutoBusOff = ENABLE`（离线后自动恢复）。
后果：**总线上没有节点（电机没接/没上电/接线反）时，只要发一帧就会被无限重传 → 收发错误计数飙升 → 反复触发总线错误/离线**。
因此动作层加了 **L3.5**：发帧后 20ms 检查 TX 邮箱是否已清空（=被某节点 ACK 过），若仍占着则 `HAL_CAN_AbortTxRequest()` **主动丢弃**，并回报 `EN NO ACK/NODE` + 日志给出排查清单。**不要**去掉这一层。

### 11.2 屏上/log 会看到什么（对照排查表）

| 现象 | 屏（行0 / 行7） | 日志 | 含义与下一步 |
|---|---|---|---|
| 只上电不接电机 | `CAN INIT OK WAITING` | `CAN status -> INIT OK / WAITING for node` + 每 10s 摘要 | CAN 外设已就绪，总线还没有帧（正常） |
| 接了电机但未使能 | 同上（**不会**变 READY） | 同上 | 厂商文档：**使能后才回传反馈帧** → 需要长按使能 |
| 电机接上且已使能 | `CAN READY 302Hz SEND` | `CAN feedback link UP` + `status -> READY` | 通道建立，**随时可发数据**；行1~5 变成真实数据 |
| 手拧输出轴 | 行1/行2 数字变化 | `fb stream: pos=..deg vel=..RPM ..`（1Hz） | 验证解析正确（角度随拧动单调变化、温度合理） |
| 长按 2s（光标在行0） | 行7 依次 `EN SENT...` →（300ms）`EN OK (FB UP)` | `-> ENABLE frame sent ...` → `EN confirmed: feedback +N frames` | 成功：电机 RGB 红→绿 |
| 长按 <2s | `HOLD <2.0s` | `hold xxx ms < 2000 ms -> not triggered` | 按久一点（2s 以上都算触发） |
| 1.5s 内连按两次 | `COOLDOWN` | `action rejected: cooldown ...` | L2 保护，等 1.5s 再按 |
| 电机没接/没上电时长按 | `EN NO ACK/NODE` | `no ACK in 20ms -> TX aborted (no node answered)` + 行6 出现 `TEC/REC/LEC` | L3.5 保护生效；查 24V / H-L / 120Ω / CANID |
| 接上了但使能后无反馈 | `EN NO FEEDBACK` | `EN sent but NO feedback within 300ms` | 查电机是否真上电、CANID 是否 0x01、H/L 是否反 |
| 光标在其它行长按 | 无变化（静默） | `LOG_D: hold ... on a read-only row -> no action` | 只读行不动作（设计如此）；M4 再给这些行挂动作 |

### 11.3 接电机测试剧本（按顺序，安全）

1. **断电**测 A 板 CAN1 座 H–L ≈ **120Ω**（板载 R80）；接电机（H↔H、L↔L、GND 共地）、电机 24V 独立供电、电机端 120Ω 开关**开** → 复测 H–L ≈ **60Ω**。
2. 烧 **v0.1.47-dev**，上电只看串口：应见 `CAN init OK ... INIT OK / WAITING for node`（**不接电机时也不会报总线错误** = 我们没在自发帧）+ `task bring-up: active=5 | free heap=xxxxx B / total=32768 B`（静态预算：5 个任务栈 2560 words=10.2KB + TCB ≈ **32.8%**，故 free heap 应在 **21~22KB** 量级；若明显偏小或 active < 5 → 有任务没创建起来）。
3. 手拧电机输出轴 → 因为未使能**不会有反馈**（正常）。
4. 光标保持在**行0**，长按 **>2s** 松手 → 期望日志 `-> ENABLE frame sent` → 20ms 内无 `no ACK` → 300ms 内 `EN confirmed: feedback +N frames`；屏行0 跳 `CAN READY xxHz SEND`、电机 RGB 红→绿、行1~5 出现数字。

## 12. M4-a：HOLD 阻尼保持 + "响应式心跳"实测结论（v0.1.49-dev）

### 12.1 实测：本电机的反馈帧是**响应式心跳**（文档口径 ≠ 实测）

- 文档 §3.1 原文："电机反馈帧ID 由命令ID 0x780 + 电机ID 组成…**电机需要使能后才会回传反馈帧**"
- **实测（v0.1.47，2026-09-15）**：光标在行0 长按 2.99s → `-> ENABLE frame sent` → **无 `no ACK`**（帧被电机应答）→ **电机 RGB 变绿（使能成功）** → 但 300ms 后 `EN sent but NO feedback within 300ms`，且此后 `rx=0`（**一条反馈都没有**）。
- 结论：**使能 ≠ 开始回传**；反馈是"收到控制帧才回复"的响应式心跳。之前台架演示能收到反馈，正是因为演示程序在 200Hz 持续发 MIT 帧。
- 因此：**要读回电机参数，必须先进入控制帧循环**（HOLD）。

### 12.2 HOLD 阻尼保持（本次实现）

| 项 | 内容 |
|---|---|
| 进入条件 | 使能帧被 ACK（L3.5 通过）→ 自动 `hold_enter()` |
| 帧内容 | `J8108_SendMIT(p=0, v=0, Kp=0, Kd=1, t=0)` → `torque = -Kd·v`（**纯阻尼**：手拧有阻力、松手不回位、不发力） |
| 频率 | 200Hz（`J8108_CTRL_PERIOD_MS=5ms`，与台架演示一致） |
| 退出条件 | ① 长按失能（先停发再发失能帧）② 看门狗：50ms 周期查 TX 邮箱是否被 ACK → 卡住则 `HAL_CAN_AbortTxRequest` + 停发 + `EN NO ACK/NODE` ③ 反馈丢失 >500ms → 停发 + `EN NO FEEDBACK` |
| 屏幕 | 行0 `CAN READY xxxHz HOLD`（对比未进入控制循环时的 `SEND`） |
| 读回参数 | 屏行1~5 实时（5Hz 刷新）+ 串口 1Hz `fb stream: pos=..rad(..deg) vel=..rad/s(..RPM) T=..Nm Tm=..C Tr=..C age=..ms` + 前 10 帧原始字节 `fb#N raw ..`（核对解析） |
| 关闭开关 | `J8108_HOLD_ON_ENABLE 0` → 使能后完全不发帧（用于验证"不发帧是否真没反馈"） |

### 12.3 首次实机 HOLD 实测（v0.1.49，2026-09-15 深夜）—— 推断成立 + 暴露 2 个 bug

**成功的部分（关键实证）**：
```
[J8108] I: -> ENABLE frame sent (hold 3570ms, ID 0x001); waiting ACK(20ms) + feedback(300ms)
[J8108] I: HOLD mode ON (enable ACKed): sending MIT damping frames v=0 Kp=0 Kd=1.0 every 5ms
[J8108] I: CAN feedback link UP (rx=1) -> motor is powered AND enabled
[J8108] D: fb#1 raw 00 07 F4 7F F7 FF 62 48 | pos=-23.559 vel=-0.01 T=-0.004 Tm=38.4 Tr=28.2
[J8108] I: EN confirmed: feedback +60 frames -> motor enabled, status now READY
```
→ **"响应式心跳"推断完全成立**：发 MIT 帧后立刻收到 0x781；`rx≈tx`（1:1 请求/应答）。
→ 实测参考值：`pos=-23.56rad（电机端）= -168.7°（输出端）`、`vel≈-0.01rad/s`、`T≈0`、`Tm=38.4C`、`Tr=28.2C`、**`byte0=0x00`**（文档标"待定"；无错误时清零 → 支持"状态/错误位"假设）。

**Bug 1：看门狗把"正在发送"误判成"无 ACK"** → 把好端端的 HOLD 反复掐断（日志 `HOLD mode ON/OFF` 循环 6 次）。
根因：判据写成"TX 邮箱非全空（`< 3`）"；而 1Mbps 下发一帧本身就要占用邮箱 ~130µs，采样点撞上就是误判。
修复：**迟滞判据** `j8108_tx_stuck(t, limit)` —— 只有邮箱**连续占用** ≥100ms 才算无人 ACK（HOLD 用 100ms、L3.5 用 20ms）；并给 L3.5 加**单次检查**标志 `s_ack_checked`（原来 `s_ack_dl_ms=0` 作哨兵会导致每轮都重进 HOLD）。

**Bug 2：掐断后数据流彻底死掉**（`rx` 卡在 66、`age` 一路涨到 23696ms）
根因：HOLD 一停 → 电机（响应式心跳）立刻静默 → 链路 LOST → 没有任何机制恢复。
修复：引入**保持意图** `s_hold_want`（使能 ACK=1，失能/放弃=0）+ **退避自动恢复**（失败 n 次则等 n×500ms 重试，上限 4 次；有进展即清零；超限打 `LOG_E` 提示"按一次重来"）；反馈流日志改为**只在数据新鲜时**打印（链路断了只由 LOST 边沿 + 10s 摘要报，不再刷屏）。

### 12.4 下一步（M4-b 候选）

- **位置保持**：把 HOLD 帧改成 `v=0, Kp=小值(如 5~20)` 即可"软回零点"；或加"当前位姿锁定"（把进入 HOLD 时的 pos 作为 p_des）
- 其余行级动作：光标到别的行长按 → 零点（需 4s）/ 重启（6s）/ 切换阻尼↔位置保持
- 告警打磨：超温反色、堵转/过载提示（反馈 byte0 疑似状态位，接电机后实测反推）

**页面刷新策略**：局部刷新（只刷内容变化的行）——整屏软 I2C ≈10ms，局部 1~2 行 ≈1.3~2.6ms，
10Hz 刷新约 **2.6% CPU**，且永远让位于 prio 5 的 200Hz 控制帧发生器。
