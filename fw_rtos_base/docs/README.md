# docs 导航（先读哪份、每份是干嘛的）

> 规则类是**已经框定下来、不可随手改**的东西；方案类是"当时为什么这么定"的来龙去脉；过程记录是施工日志与证据。

## 每份文档"什么时候该读"

| 你的问题 | 读这份 |
|---|---|
| 这个工程怎么加新模块/新器件？宏怎么用？ | `1_规则/规范_功能宏与模块化.md` |
| 代码风格、命名、注释、提交前检查什么？ | `1_规则/规范_编码规范.md` |
| 串口发什么命令、回包长什么样？ | `1_规则/操作手册_串口命令.md`（用法）+ `协议_串口控制_v1.md`（口径） |
| 怎么验收台架/怎么上机测？ | `1_规则/测试手册_8108串口控制.md` |
| 代码在哪儿、这个函数干啥的？ | `code/00_总览与阅读指南.md` → `code/_函数地图.md` |
| 当初为什么这么定？（彩屏/界面/模块化） | `2_方案/*` |
| 这次改造做了啥、踩了什么坑？ | `3_过程记录/日志_模块化改造.md` |
| 规范到底落实了没有？ | `3_过程记录/评估_规范落实.md` |

## 维护约定（新增文档放哪、怎么命名）

| 类别 | 放哪 | 命名前缀 | 判断标准 |
|---|---|---|---|
| 规则/口径 | `1_规则（既定事实）/` | `规范_` / `协议_` / `操作手册_` / `测试手册_` | **改了会影响所有人**，必须评审后改 |
| 方案 | `2_方案（定稿设计）/` | `设计_`（架构/硬件论证）/ `编码方案_`（分文件规格）/ `实施方案_`（分步计划） | 写功能**之前**定稿；落地后归档留证 |
| 过程 | `3_过程记录/` | `基线_` / `日志_` / `评估_` | 时间序记录，**不是规则**，不要拿它当规范用 |
| 第三方 | `9_第三方参考/` | 索引 `README.md` 指向仓库外实体 | 厂商例程/数据手册等，不进固件版本库 |

**铁律两条**：
1. **规则与实现必须一致** —— 发现不一致，要么改代码、要么改规范（并说明修订日期）；不允许"规范写 A、实现做 B"长期共存。
2. **能机械检查的规则要变成断言**（`make verify` / `make profiles`），文档里只留"为什么"。
